# Архітектура MVP

Модульний моноліт ASP.NET Core 8 / EF Core 8 / PostgreSQL 16 та React 18 + TypeScript. Одна БД розділена схемами `identity`, `assessment`, `groups`, `billing`, `platform`. Спільний Infrastructure-проєкт реалізує інтерфейси модулів без створення додаткових проєктів для кожного адаптера.

## Основний шлях

```mermaid
sequenceDiagram
    actor Student as Учень
    participant Web as React
    participant API as ASP.NET Core
    participant DB as PostgreSQL 16
    Student->>Web: Реєстрація / вхід
    Web->>API: Профіль і пароль
    API->>DB: BCrypt-хеш, акаунт, сесія
    API-->>Web: Access JWT + HttpOnly refresh-cookie
    Student->>Web: Діагностика
    Web->>API: Варіант відповіді, version, requestId
    API->>DB: Блокування сесії; відповідь, theta, наступне питання
    API-->>Web: Питання без ключа відповіді / результат
    Student->>Web: Курс і розклад
    API->>DB: Транзакція: учень → курс → група FOR UPDATE
    API->>DB: Enrollment Reserved на 15 хвилин
    API-->>Web: Резерв і зафіксована ціна
    Student->>Web: Тестова оплата
    API->>API: Mock-шлюз поза блокуванням БД
    API->>DB: Повторна перевірка резерву; Active + запис платежу
    API-->>Web: Запис підтверджено
```

## Identity

Паролі BCrypt cost 11; публічна реєстрація дозволяє тільки ролі Student та Parent. Access JWT живе 60 хвилин, refresh-сесія — 14 діб; refresh-токени зберігаються у БД лише у вигляді SHA-256-хешів і ротуються. Повторне використання старого refresh-токена відкликає його сесію. Кожний авторизований запит перевіряє активність користувача й сесії; вихід відкликає також виданий JWT. Клієнт тримає access-токен у пам’яті, refresh — у HttpOnly SameSite-cookie, а не в localStorage.

До 16 років акаунт неактивний до підтвердження батьків: окремий email, зв’язок у БД, одноразовий код на 24 години, до 5 спроб. Код хешується; локальна тестова доставка зберігає лист у `.local/mail`. Платежі дитини дозволені тільки підтвердженому батьківському акаунту. Development-пошта відсутня у Production API.

## Assessment

Сервер сам звіряє відповідь із банком. Клієнт не передає `correct`, theta чи остаточний бал. Версія сесії та поточне питання перевіряються під блокуванням рядка тесту; унікальні індекси захищають від дубля відповідей. Повторення того самого requestId із тими самими даними повертає збережену відповідь без нового розрахунку. Інший payload з цим ключем дає конфлікт.

Elo: P = 1 / (1 + 10^((b − theta) / 20)); K = 8 для відповідей 1–5, 4 для 6–10, 2 надалі. Theta обмежена 0–100. Після 15 відповідей сесія може завершитися, якщо розмах останніх п’яти theta < 1; після 20 завершується завжди. MathScore округлюється від нуля. Результат і дата завершення записуються в акаунт. Повторне проходження — через 30 діб.

Нові редакції завдання створюють новий запис; опубліковане питання з попередньої сесії не переписується. Сесія зберігає питання, версію, складність і відповідь. Початковий банк містить 40 завдань для кожного з 6 контекстів; це навчальні дані з орієнтовною складністю.

## Groups та оплата

Підбір фільтрує курс, вікову когорту та слот; перевіряє розкид знімків MathScore ≤ 5 серед Active та чинних Reserved. Ранг не є фільтром. Порядок блокувань для мутацій запису: учень → курс → група. Блокування курсу навмисно серіалізує створення груп для одного курсу: проста передбачувана реалізація для MVP. Для великого навантаження це місце потребуватиме вимірювання й точнішої синхронізації.

Резерв — `Enrollment` зі статусом `Reserved`, а не окрема сутність SeatReservation. В історії може бути будь-яка кількість записів; зайнятих місць одночасно — до 5. Термін резерву 15 хвилин. Прострочені резерви одразу не враховуються при читанні та підборі; статус матеріалізується під час наступної мутації, фонового воркера для цього MVP немає. Унікальний активний/зарезервований запис перевіряється за учнем і курсом.

`ActiveCount` рахує тільки підтверджених. Forming — 0–2, Open — 3–4, ClosedFull — 5. Ціна й бал фіксуються у записі. Платіжний адаптер явно тестовий, викликається поза транзакцією; перед підтвердженням резерв повторно читається під блокуванням. Для простроченого резерву записується тестова компенсація; реальних грошей немає. Повторні запити захищені ключами ідемпотентності та унікальним індексом платежу на Enrollment.

## Межі наступних етапів

Learning, Gamification та зовнішня доставка Notifications залишаються контрактами/початковими доменними типами. Повний баланс, навчальні заняття й розгортання не удають завершені можливості. У Лаб №5 можна розвивати інтеграції та завершувати погоджений обсяг; Лаб №6 — формальний набір unit/component/system/concurrency/load перевірок і матриця покриття. Робочий MVP уже дозволяє виконати основний користувацький шлях, але не є всією майбутньою платформою.
